### 12. [CRITICAL] Gateway payments can never reach the billing ledger — `record_billing_payment` rejects every service-role caller, and the webhook discards the error

- **Dimension:** silent-failures
- **Location:** `src/routes/api/public/payments/$provider/webhook.ts`:114 (+ the RPC's own guard)

**Impact:** `record_billing_payment` opens with
`IF NOT (is_tenant_owner(auth.uid(), _tenant_id) OR is_platform_admin(auth.uid())) THEN RAISE EXCEPTION 'Not authorized'`.
The webhook calls it on `supabaseAdmin` (service role, `persistSession:false`, no user JWT),
so `auth.uid()` is NULL and the guard always raises. The call site does not destructure
`error`, and supabase-js *resolves* rather than throws, so the enclosing `try/catch` never
fires. Net effect once a gateway is live: parent pays → `payment_transactions.status` flips to
`'success'` → `billing_payments` / `billing_payment_allocations` / `billing_invoices.amount_paid`
are never written → the invoice stays unpaid and the student shows as a defaulter. The run is
then made non-retryable: `payment_webhooks.processed` is set true, a redelivery with the same
`event_id` short-circuits to "Duplicate ignored", and a redelivery with a new `event_id` is
skipped by `if (tx && tx.status !== "success")`. Money collected, permanently unrecorded, 200 OK
returned to the gateway.

**Live blast radius today:** almost certainly zero — this fires only when a tenant has a
configured payment gateway, and `/dashboard/payment-settings` has been effectively unreachable
(Phase 1/2 history). This is a loaded gun, not a fired one. It must be fixed *before* any
tenant is onboarded onto online payments, not after.

**Fix:** two parts, both required.
(a) Make the RPC accept a trusted server-side caller — `IF auth.uid() IS NOT NULL AND NOT (...)`,
or add an explicit `_actor_id` parameter — otherwise no webhook or cron can ever record a payment.
(b) At the call site: `const { error: rpcErr } = await supabaseAdmin.rpc(...); if (rpcErr) throw rpcErr;`
and move the `payment_transactions` status flip to *after* a successful ledger write, so a failure
leaves the event redeliverable.

<details><summary>Verification</summary>

Read the RPC body at `supabase/migrations/20260714191332_...sql:499-560`; the guard is at 522-524
and `is_tenant_owner` (same file, 15-24) is `SELECT EXISTS(... FROM profiles WHERE user_id=_uid ...)`,
false for NULL. Grepped every migration for `FUNCTION public.record_billing_payment` — exactly one
definition, never replaced, so the guard is live. Read `webhook.ts:106-128`: the `.rpc(...)` result
is not destructured at all. Cross-checked the other four call sites: `manual.functions.ts:167,309`
and `billing.ts:402` use a caller-scoped client (owner JWT — these work), while
`service.functions.ts:219` has the *same* service-role defect but does destructure `error`, so it
fails loudly instead of silently. Root cause is shared; only the webhook is silent.
</details>

### 17. [HIGH] Billing V2 never reads `students.custom_fee`, and the add-player path never passes `gender` — the same student is billed differently depending on which door she came through

- **Dimension:** money-fees

### 18. [HIGH] Quick-collect idempotency key is `(student, period, amount)` — a second equal partial payment in the same month is silently swallowed and reported as success

- **Dimension:** money-fees
- **Location:** `src/components/fees/CollectionsPanel.tsx`:15 (used at :792)

**Impact:** The key is `fees:quick:${studentId}:${period}:${amount}`. `record_billing_payment`
short-circuits on a duplicate key — `SELECT id INTO existing_id ... IF existing_id IS NOT NULL THEN RETURN existing_id`

`billing.ts:442`) and hold it in component state, so it dedupes true double-submits (the thing
idempotency is for) instead of deduping distinct payments.

### 26. [HIGH] A failed `submit_registration` after `signUp` leaves a permanently orphaned auth user who can never register again

- **Dimension:** auth-flows
- **Location:** `src/routes/register.tsx`:445 (failure return at :557-561)

**Impact:** The auth account is created *before* the registration row. `submit_registration` raises on
"Academy not accepting registrations", "Invalid fee plan", "Invalid batch", or its own rate limit — all
reachable, because fee plans and batches come from a cached `useQuery` and can be deactivated between

retries → `signUp` fails "already registered" → they sign in → `my_post_login_route()` returns `'none'`

self-service recovery, that email is burned.**

anon), then `signUp`, then `attach_applicant_to_registration`. If `signUp` must stay first, handle the
failure explicitly: delete the just-created auth user via a service-role server fn, or detect
"signed-in user with zero registrations and zero students" at sign-in and route them to a resumable
registration form. Also stop silently skipping the linking block when `applicantUserId` is null.

### 27. [HIGH] `createTenantOwner` only searches the first 200 auth users — past that threshold, an existing owner email leaves a live tenant with no owner

- **Dimension:** auth-flows

success screen and told they can sign in with phone. Later, the phone branch of sign-in fails with the
generic "We couldn't sign you in with those details" and they have no way to learn that only their email
works. `reason: 'no_registration'` in particular indicates the applicant link itself failed — a real
signal being discarded.

**Fix:** Capture the result; when `attached === false`, change the success copy to "Sign in with your
email address (phone sign-in isn't available for this account)", and log `reason` so the benign
`phone_in_use` is distinguishable from the diagnostic `no_registration`.

### 29. [HIGH] `auditStudentIdentity` stamps every repaired student `SAI0001`, the unique-index rejection is swallowed, and the `card_token` is lost with it

- **Dimension:** silent-failures
- **Location:** `src/lib/admissions/audit.functions.ts`:37 *(same file as confirmed finding 9 — that one covers the missing auth, this one the data corruption)*

**Impact:** `.select("id", { count: "exact", head: true })` returns no rows — the count lives on `count`,
and `data` is null — so `countData?.length` is always undefined and `nextNum` is unconditionally 1. Every
student repaired through this path is assigned `SAI0001`. `students_tenant_player_id_uidx`
(`20260708071446:119`) rejects the second and every subsequent one, the update's error is never
destructured, and the handler still returns `{ success: true, player_id: "SAI0001" }`. Because
`card_token` is set in the **same patch object**, it is rolled back too — and that token is what the QR
student card and the check-in scanner use, so the student can never be scanned for attendance. All three
callers (`activate.$token.tsx:40`, `dashboard.registrations.tsx:113`, `dashboard.activation.tsx:60`)
display an ID that does not exist in the database.

**Fix:** Read `count`, not `data.length`. Better: allocate the ID in a SECURITY DEFINER function with a
per-tenant sequence under a row lock so concurrent activations cannot collide. Destructure and return the
update error, add the missing `.eq("tenant_id", tenantId)`, and split `card_token` into its own write so
an ID collision cannot take the QR token down with it.

### 30. [HIGH] `approveRegistration` never checks the `registrations` update — a failure produces a duplicate student on the next approval attempt

- **Dimension:** silent-failures
- **Location:** `src/lib/admissions/admissions.functions.ts`:86 (and `waitlistRegistration`:141)

**Impact:** Every other write in this handler is checked (`if (error) throw error` at :79 and :83), but
the `registrations` update is not — and it carries the only link back from the registration to the
newly-created student. It runs on the user-scoped `context.supabase`, while `assertAdmin` admits any
`user_roles` 'admin', who may not satisfy the registrations UPDATE policy. If it errors or matches zero
rows, the handler still returns `{ ok: true }` and the dialog reports success. The registration stays
pending with `student_id` null, so the next Approve click takes the INSERT branch at :81 and creates a
**second duplicate student** with its own activation token and its own fee obligations. In
`waitlistRegistration` the unchecked update is the *only* write, so a failure means the toast says
"waitlisted" while nothing changed at all.

**Fix:** Destructure and throw on both, add `.select("id")` and throw on zero rows so an RLS no-op is not
mistaken for success. `rejectRegistration` (:114) and `requestRegistrationChanges` (:365) already do this
correctly — match them.

### 31. [MEDIUM] The scorer closes innings 1 with an unchecked update inside a `try/catch` that cannot catch it — and a second copy of the function never closes it at all

- **Dimension:** silent-failures
- **Location:** `src/routes/scorer.$matchId.tsx`:627 (duplicate at :1793)

**Impact:** supabase-js resolves with `{ error }` rather than rejecting, so the `try/catch` around the
`mc_innings` "completed" update is dead code for that call — it can only catch a rejection from
`session.startInnings`. If the update fails or matches zero rows, innings 1 stays not-completed while
innings 2 is created, and the scorer sees the green "Innings 2 · target N" toast. The match then has two
non-completed innings rows, and every consumer that resolves the active innings by status (public live
match center, scorecard, `mc-innings-derive` → `mc-statistics-engine`) sees an ambiguous state
mid-match. Verification also found a **second `startSecondInnings` in the same file (:1793) that starts
innings 2 without closing innings 1 at all** — worth resolving which one is live.

**Fix:** Destructure and throw so the existing catch fires, and only call `startInnings` after the close
succeeds. Reconcile the duplicate function.

### 32. [MEDIUM] Knockout bracket progression writes the winner with no error check, silently leaving an empty semi/final slot

- **Dimension:** silent-failures
- **Location:** `src/lib/mc-fixture-engine.ts`:762

**Impact:** This is the winner-propagation step after a match is locked. Neither the
`mc_tournament_rounds` update nor the `mc_matches` update is checked, and the function returns void, so
nothing upstream can detect a failure. It uses the user-scoped client, and the person locking the score
is often a scorer rather than the owner. On failure the next round keeps `team_a_id`/`team_b_id` null and
the pre-created next-round match keeps its placeholder teams: the bracket renders a blank slot with no
error anywhere and has to be hand-repaired in the database mid-tournament. The same unchecked shape
exists in the bracket-wiring loop at :653-666.

**Fix:** Destructure and surface both errors and return a result the caller can act on. Because the two
writes must both land or neither, consider moving the propagation into one SECURITY DEFINER RPC.

### 33. [MEDIUM] A failed ball write silently removes the ball from the scoreboard with console-only logging

- **Dimension:** silent-failures
- **Location:** `src/hooks/use-scoring-session.ts`:532

**Impact:** The optimistic ball is applied synchronously and the network write is deliberately not
awaited (documented at :505-512 — a correct choice for a phone at a ground). But the **only** notification
on failure is `console.error`, where nobody has devtools open. A scorer on a weak connection taps a
boundary; the write fails; the score jumps back down by 4 several seconds later with no toast and no
retry affordance. Worse, when the failed ball was *not* the latest (`wasLatest` false), the
striker/bowler pointers are deliberately left alone — so local state now reflects a rotation that assumed
a ball the server never received, and every subsequent ball's sequence numbering derives from
`priorEvents`, which no longer matches the server's list. This is the only mutation in the codebase with
no `toast.error` path at all.

**Fix:** Add a `toast.error("Ball not saved — tap to retry")` in the catch and expose the failure through
the hook's existing `error` state. Add a bounded retry of the same `optimistic.id` before reverting, and
block further input until the queue drains when a revert removes a non-latest ball.

### 34. [MEDIUM] The mirror trigger derives payment `type` by substring-matching the owner's free-text note

- **Dimension:** money-fees
- **Location:** `supabase/migrations/20260731084306_...sql`:32 (only definition of `mirror_billing_payment_to_legacy`)

**Impact:** `v_type := CASE WHEN remarks ILIKE '%registration%' THEN 'registration' WHEN remarks ILIKE '%admission%' THEN 'admission' ELSE 'monthly' END`,
where `remarks` is the owner's free-form note concatenated onto the period tag
(`CollectionsPanel.tsx:10-14`, placeholder "e.g. paid half, rest next week"). An owner collecting a normal
₹1,000 monthly fee who types "admission ke time ka baaki" produces a `payments` row typed `'admission'`.
The dashboard KPI filters `.eq("type","monthly")`, so that ₹1,000 of genuinely collected cash vanishes
from "Collection this month" *and* the same student is simultaneously counted as still pending. The
receipt PDF also prints "Registration fees" (`receipt-pdf.ts:106-110`).

**Fix:** Stop inferring type from prose. Encode it explicitly the way the period already is — write
`[type:monthly]` / `[type:registration]` from the caller and parse that tag, defaulting to `'monthly'`.
Restrict the ILIKE fallback to the auto-generated `approve_registration` remark, which has a stable prefix.

### 35. [MEDIUM] Mid-month joiners are due on the dashboard but permanently skipped by the reminder cron

- **Dimension:** money-fees
- **Location:** `src/routes/api/public/hooks/fee-reminders.ts`:62

**Impact:** The cron does `if (joined && joined > periodStart) continue;` where `periodStart` is the 1st
of the current month. The canonical rule (`fees.ts:58-59`) excludes only months strictly *before* the
joining month. A student joining 15 Aug is `pending` for 2026-08 on both the Collections tab and the KPI,
but the cron skips them — so every mid-month joiner silently misses their first reminder cycle while the
fee register shows the debt. The cron also applies the calendar-month rule unconditionally, ignoring
`tenantFeeCycle`, so joining-date-cycle tenants get reminders keyed to the wrong period entirely.

**Fix:** Replace the ad-hoc check with a call to the shared
`studentDue({ cycle: tenantFeeCycle(t), joinedAt, selectedMonth, paidPeriods, today })` and queue a
reminder whenever it returns `'pending'`, using the returned `period` for `reminder_logs`.

### 36. [MEDIUM] `getDailyBrief` and `generatePeriodicBrief` bypass RLS with `supabaseAdmin` and perform no role check

- **Dimension:** nevorai-ai
- **Location:** `src/lib/nevorai/brief.functions.ts`:151 (and `reports.functions.ts`:161-169)

**Impact:** The handler selects only `tenant_id` from `profiles` — role is never selected or checked —
then `buildBriefForTenant` runs everything through the service-role client. The only gate is the
client-side `<OwnerOnly>` wrapper, whose own comment asserts "Data access is still enforced by RLS" —
false for this path. A tenant admin or coach, deliberately excluded from `payments` by the owner-only RLS

becomes a live finance leak to every non-owner staff member.** Fix them together.

**Fix:** Assert owner (or platform admin) server-side before building the brief, via the same helper the
rest of the codebase uses. Do not rely on `<OwnerOnly>`.

# Synthesis — the verdict, the themes, and the fix order

## Plain-language verdict

**AcademyOS is not in danger of falling over, but it is quietly lying to its users in several
places at once, and it has one genuine security hole.**

Across 1158 unreviewed commits, 36 confirmed defects, and 3 false alarms, almost nothing found was
a crash, a data loss, or an outage. That is the good news, and it is real: the tenant-isolation
model (RLS + `is_tenant_member`/`has_role`) held up across 92 tables, the SECURITY DEFINER
functions pin `search_path`, webhook signatures verify with replay protection, and no secrets
leaked (the secrets-injection dimension returned zero findings).

The bad news is the shape of what *was* found. The dominant failure mode is **a wrong number
displayed confidently, with no error anywhere**. The owner's Fees screen and the owner's dashboard
KPI disagree about who has paid. NevorAI's Daily Brief says "the academy is on track" while the
Fees screen shows real defaulters. The public match page shows one score and the scorecard
underneath it shows a different one. The WhatsApp reminder demands ₹1,000 from a family charged
₹600. A second ₹500 cash payment is accepted, discarded, and reported as "marked paid ✓". In every
one of those cases the software is confident and wrong — which, for a product whose entire pitch is
"the owner can trust the numbers", is the worst possible failure class.

Two things need naming beyond the finding list:

1. **One real security hole:** `getTenantPaymentSetup` (finding 2) hands any logged-in user any
   academy's bank account number, IFSC and UPI ID. Tenant IDs are anon-visible. This is the only
   finding where an outsider gains something they should not have, and it should be fixed first.
2. **One regression:** the NevorAI Daily Brief reading empty `billing_*` tables (finding 13) is the
   *same bug Phase 2 already fixed* in three other places, reintroduced in a fourth. The fix held
   where it was applied and the underlying trap — two money tables, one empty — was left in place
   for the next writer to fall into.

## Systemic themes

**1. Two money systems, still.** Legacy `payments` holds the real data; `billing_*` is the newer,
better-designed, nearly-empty one. Findings 12, 13, 17, 36 and the Phase 2 fixes are all the same
root cause: *which table is the truth depends on which file you are reading.* Every new surface is
a coin flip, and the flip is silent because an empty table returns `[]`, not an error. **This trap
will keep producing findings until it is closed by decision, not by patching.** Adarsh owes a
product call here: either build the owner UI that makes `billing_*` real and backfill it, or
formally park V2 and make `payments` the documented single source. Patching the fourth reader
without making that call guarantees a fifth.

**2. `supabase-js` resolves, it does not throw — and half the codebase writes as if it throws.**
Findings 12, 30, 31, 32 and the `try/catch` in 28 are all this one language-level fact.
`await supabase.from(...).update(...)` inside a `try/catch` looks safe and is not. This is the
single highest-leverage lint rule the project could adopt: *every* supabase call must destructure
`error`. That one rule would have caught five findings, including the critical one.

**3. Effective fee is computed in six places and correctly in three.** `custom_fee ?? (gender pricing ? female_amount : amount)`
is implemented in `dashboard-queries.ts`, `CollectionsPanel` and `StudentProfilePanel` — and
*not* in `billing-enrollment.ts`, the reminder cron, or the NevorAI finance tool (findings 15, 17,
20). Same for "which payments count as paid this period" (findings 16, 19, 34, 35). These are not
six bugs; they are one missing shared helper, cloned six times with three of the clones stale.

**4. Role checks read `profiles.role`; role *writes* go to `user_roles`.** Findings 7 and 14, plus
the already-shipped Phase 26 fix, are the same divergence. `profiles.role` is not dead — it still
has live readers making authorization decisions — so it cannot be deleted, but it is also never
cleared on demotion. Every new authorization check written against it inherits a stale answer.

**5. Pages get built and then orphaned from navigation.** Findings 22, 23, 24 — plus the earlier
`/dashboard/payment-settings` orphaning that is *why* `billing_*` stayed empty in the first place.
This is not cosmetic: an unreachable page means a feature that was paid for, works, and earns
nothing. `/platform-admin/payment-settings` being dark is why AcademyOS cannot collect its own
subscription revenue through the product.

**6. Migration-file archaeology is unreliable, and this audit proved it twice more.** All three
refuted findings were defects that a later migration had already repaired. This is now the third
independent confirmation (see the Phase 27 and Phase 28 notes in memory). **Rule going forward: any
finding whose evidence is a `.sql` file must be confirmed against live `pg_policies` / `pg_proc`
before it is acted on.** By contrast, the TypeScript findings in this batch confirmed at 25/25 —
because for `.ts` files, the current file *is* the deployed state. That asymmetry explains the
whole difference between Part 1's ~1-in-5 refutation rate and Part 2's zero.

## Recommended fix order — five units of work

Sequenced by *risk removed per unit of Lovable effort*, and batched so each unit is one coherent
paste with one testable outcome. Do not reorder units 1 and 2.

**Unit 1 — Security + dead-feature P0** *(prompt written: `LOVABLE-PROMPT-34`)*
Findings 2, 1, 4/5/6, 3, 7. The bank-details leak, the reversed-arg policy that keeps parent
billing history permanently empty, the three public match surfaces hand-rolling scoring math, the
dead platform-admin push auth, and the fired-coach-keeps-access path. One security fix, one
migration, one shared-engine consolidation, two one-liners. Highest severity-to-effort ratio in the
list, and nothing in it depends on a product decision.

**Unit 2 — The money-truth decision, then the money fixes**
Findings 12, 13, 17, 36, and 18. **Blocked on Adarsh's call**: build Billing V2 for real, or park
it. Once decided: fix `record_billing_payment`'s service-role guard + the webhook's discarded error
(12) *before* any tenant is put on online payments; repoint the Daily Brief off the empty tables and
add the missing server-side owner check in the same pass (13 + 36 — fixing 13 alone turns 36 into a
live finance leak, so they must ship together); fix the idempotency key that eats partial cash
payments (18 — this one is independent of the decision and can ship immediately).

**Unit 3 — One effective-fee helper, one paid-set helper**
Findings 15, 17b, 19, 20, 16, 34, 35. Extract `effectiveMonthlyFee(student, plan, tenant)` and
`paidPeriodsFor(tenantId, periods)` into shared helpers and call them from `billing-enrollment`,
the reminder cron, `financeSummaryTool`, `CollectionsPanel` and `fetchKpis`. This is refactor-shaped
rather than patch-shaped on purpose: it is the only way theme 3 stops recurring. One unit, six
findings, and the owner's screens start agreeing with each other.

**Unit 4 — Registration and onboarding integrity**
Findings 25, 26, 30, 27, 29, 28. The changes-requested redirect loop, the orphaned auth user, the
duplicate-student-on-retry, the 200-user owner-lookup ceiling, the `SAI0001` collision, and the
discarded phone-attach result. All in the funnel that turns a stranger into a paying student —
which makes this the unit with the most direct revenue exposure after unit 2. Fix 27 before the
"100 tenants" push, not during it.

**Unit 5 — Navigation, error surfaces, and the supabase-error lint rule**
Findings 21, 22, 23, 24, 31, 32, 33, plus the frontend-ux mediums. Restore the platform-admin nav
rows, link the widget editor and NevorAI health, default the three unimplemented widgets off, add
the missing scorer/bracket error checks and the missing scorer toast, and add the lint rule from
theme 2 so this class stops being reintroduced. Cheapest unit; do it when the higher-risk ones are
landed.

## What is explicitly NOT recommended

- Do not touch `delete_student_data_v2`, the 2-arg `has_role` overload, or the attendance-QR
  policy. All three were verified as already-correct in the deployed state.
- Do not backfill or read-swap onto `billing_*` before unit 2's product decision is made.
- Do not delete `profiles.role`. It still has live readers (finding 7, finding 14); it needs
  migrating, not deleting.

## Cost note

Part 1 cost roughly $240 of a $292 session (one 19-agent workflow, ~1.5M subagent tokens) and
produced 11 confirmed findings. Part 2 verified 25 findings, ran the missing dimension, and wrote
the synthesis inline with batched greps and targeted reads — no subagents. The lesson from Part 1
holds and is now quantified: **for verification work against a local repo, inline batched reading
beats fan-out, because verification is mostly `grep` plus judgment, and judgment does not
parallelise cheaply.**
